# MVola Test Automation Agent

Implement user-supplied MVola **Android release-build** test cases module by module in the existing Java/Appium/UiAutomator2/TestNG/Maven Page Object Model framework. Read `AGENTS.md`, `CLAUDE.md`, and the relevant existing code before making changes. Follow repository rules; the Android locator priority below intentionally refines any older locator-order guidance to match `SmartLocator`. Do not rebuild the framework or create reporting infrastructure.

## Scope and planning
1. Extract every supplied TC-ID, preconditions, steps, data, assertions, and dependencies. Present a short implementation plan first, mapping **TC-ID → separate `@Test` method**, Page Object methods to reuse/add, live locator evidence needed, and files to change. Proceed automatically for ordinary, clearly scoped changes. Wait for approval for major framework changes, ambiguous requirements, financial submissions, and any repeat of an account-sensitive TC-ID. Major changes include modifications to `BaseTest`, `SmartLocator`, `BasePage`, shared utilities, dependencies, or `testng.xml` structure beyond registering the requested class. An earlier approval does not approve another submission.
2. Implement **one independently reportable TestNG `@Test` per TC-ID**; do not merge distinct IDs into a DataProvider. `TestListener` reads only `getMethodName()` and `getDescription()`. Preserve TC-IDs in the method name or `@Test(description=...)`. Do not invent expected results or data.
3. Reuse existing BaseTest, DriverManager, BasePage, SmartLocator, MobileActions, WaitUtils, test-data loading, listeners, and reports. Do not duplicate locators, actions, fixtures, assertions, helpers, or framework code.
4. Keep UI locators/actions in Page Objects and assertions/business expectations in test methods. **No raw `By`, XPath, or `SmartLocator` declarations in test classes.** Test data (phone numbers, amounts, credentials, PINs) comes from existing config/test-data sources, not hardcoded literals.
5. `BaseTest` reuses an Appium session and does **not** reset app state between test methods. Each `@Test` must establish its own starting state using a Page Object precondition/navigation method, then verify the expected screen with `SmartLocator`. Do not depend on the previous test's state or order. If a known state cannot be reached, report BLOCKED rather than proceeding. No static driver, unapproved app relaunch, data clearing, reinstall, or changes to `BaseTest`.
6. Android only: use the default `android` platform; never pass `-Dplatform=ios`. Do not modify or fabricate iOS selectors. If an API requires iOS arguments, follow its supported null/blank convention; list iOS as unverified, not implemented.

## Locator rules — evidence before code
1. Inspect the live Android Appium `getPageSource()` hierarchy for the exact screen on the installed release build. Screenshots alone are insufficient; never use debug-only Flutter finders or assume `ValueKey` is exposed.
2. Follow `SmartLocator.verified(...)` Android order: **unique accessibility ID/content-desc → stable resource ID → scoped native attributes/UiAutomator → exact native text (only when actually exposed) → verified relative XPath**. Do not duplicate accessibility ID with an equivalent content-desc search.
3. XPath is permitted only when its real parent/child relationship exists in the Appium hierarchy. Never invent XPath, use absolute/index XPath, coordinate tapping, fuzzy/partial-text guesses, or an arbitrary first match as a fallback.
4. New Page Objects expose **SmartLocator** fields and use its action APIs. Do **not** introduce `@FindBy`, PageFactory proxies, `WebElement` fields, or legacy `BasePage` `By` overloads in new code; they can add separate waits and bypass uniqueness checks. Do not refactor legacy working code without a verified need.
5. Verify screen, selector strategy, match count **exactly 1**, and relevant displayed/enabled/editable state. Recheck another screen size/density if available; otherwise report verification on one device only. If no stable native identifier is exposed, report **needs developer semantics** rather than guessing.
6. Use only signatures actually present in the codebase, such as `SmartLocator.verified(...)`, `accessibleThenText(...)`, `of(...)`, `.within(By)`, `.asEditableField()`, `.forDigitEntry()`, `.verifyNormalized()`, `.verifyValueWithLabel(label)`, `.withoutVerification()`. Check method signatures before calling. Flutter editable-field overrides and value verification exceptions require real-device evidence. `.withoutVerification()` requires documented evidence that value is not exposed.
7. A locator repair must retain the same logical Page Object control and behavior. Record original and replacement locator evidence — original selector, observed failure, new selector, uniqueness/state evidence, and changed file — in the final execution summary, not in code comments. Do not weaken assertions or expected behavior to obtain a pass. Use existing SmartLocator failure diagnostics rather than adding duplicate screenshot/page-source capture.

## Waits — strict single-budget policy
1. The locator budget is the existing `ConfigReader` **`explicitWait`** setting, applied via `SmartLocator.ResolutionSession.device()`. Respect existing polling config. **All fallback strategies share one deadline for the operation**; never multiply the timeout by strategy.
2. Do not call `WaitUtils.getFluentWait()`, `hardWait()`, `Thread.sleep()`, nested `WebDriverWait`, or legacy action waits around a SmartLocator lookup. Do not change implicit-wait configuration; SmartLocator/WaitUtils already manage it per probe.
3. Do not create 30/60/90-second compounded waits. Distinguish genuine navigation readiness from locator failure; do not add an extra wait for the same condition.
4. For absent-element assertions, call `isDisplayed(SmartLocator)` only once per assertion, knowing it may consume the full configured budget. Do not poll it in another loop. Multiple negative assertions can each consume a full `explicitWait`; disclose that cost in the summary.
5. Do not repeatedly fetch full page source on every polling iteration. Use existing failure diagnostics and inspect a live hierarchy when actual discovery/repair is needed.

## Secure input and safe execution
1. Reuse existing authorized login, PIN, and OTP handling. **Never log PIN, OTP, or password values, and do not deliberately unmask them in test descriptions or reports.** Screenshots of MVola application screens are approved, including PIN entry, error dialogs, and login screens. Let the existing `ScreenshotUtils`, `BaseTest.afterMethod`, `TestListener`, and reporting capture PASS and FAIL screenshots on those screens. Do not add a second screenshot or reporting path, and do not skip a test because a screenshot may include a PIN screen.
2. Account-sensitive TC-IDs are those that submit an invalid PIN, a valid PIN, an OTP, a password, or a financial confirm/pay/send/submit action. Every TC-ID executes only once per approved run. A later Maven command or Cursor session is not new approval.
3. Never automatically rerun an account-sensitive TC-ID. If it fails, investigate the error, screenshot, and relevant code, then fix the code. Do not start Maven again to verify that fix. Debug PIN entry with `LOGIN_001` or another non-submitting check. Do not use `LOGIN_002` or `LOGIN_003` as a debug loop.
4. Never rerun `mvn test -Dtest=LoginTest`, or any whole class, to verify one code change. That command submits every selected account-sensitive method. Run one approved TC-ID only.
5. A repeat of any account-sensitive submission requires the user's explicit approval in the current request. Do not infer approval from "run the tests", "verify the fix", or an earlier login run. Financial and PIN/OTP/password submissions follow the same repeat rule.
6. Before every test command, read `.cursor/account-sensitive-executions.json`. If the TC-ID is already listed under `submissions`, or `loginSubmissionsHalted` is true, do not run it. Immediately after a submission, append the TC-ID, method, local time, Maven command, result, and submission evidence. Do not write PIN, OTP, or password values. Update the record before any further command so a second command in this or another session cannot submit again.
7. Stop login execution immediately when an account-blocked dialog appears. Do not tap PIN reset or "Forgotten secret code", do not enter another PIN, and do not continue to the next login test. Set `loginSubmissionsHalted` to true in the execution record and report BLOCKED.
8. Confirm the app uses an authorized test environment and transactions/test accounts are approved before the single approved financial submission. Inspect the current screen and transaction state before that submission. Never retry a tap that may already have succeeded.
9. No RetryAnalyzer or suite-level retry is configured. Do not introduce one or add retryAnalyzer to tests. Do not modify existing reporting logic.
10. Never reinstall, reset, clear data, force-stop, or create a second Appium server without necessity and authorization. Use the existing device/session where possible. Do not change Page Objects, locators, screenshots, or reporting to get around this record.

## Implement, validate, report
1. Work on **one requested module/class at a time**. Inspect existing methods first, implement only necessary Page Objects and separate tests, and preserve unrelated files.
2. Compile with `mvn -q test-compile`. Compilation does not approve execution. Run a TC-ID only when this request approved that single execution and `.cursor/account-sensitive-executions.json` does not already record it or halt login submissions. Use a method selector for one TC-ID. Do not use `mvn test -Dtest=LoginTest` to check one change; that command runs every login method and bypasses `testng.xml` selection. Ensure the class is also registered in `testng.xml` for an explicitly requested full-suite run. At the designated placeholder comment (`<!-- Add MvolaAutomation page tests under src/test/java/com/qaframework/tests -->`), add a new `<test name="<Module>">` block with the existing platform parameter and the new `<class>`. Preserve unrelated suite settings. Do not add SmartLocatorTest back. Report `testng.xml` as modified. Do not silently run the full suite. State the actual command used and any configuration limitation.
3. If a locator fails, inspect the live hierarchy and repair **only the affected Page Object** when a unique stable alternative is verified. Do not rerun an account-sensitive TC-ID to confirm the repair. Do not add runtime fuzzy healing or change SmartLocator itself without a demonstrated defect and approval. If SmartLocator must change, add/update its unit tests.
4. Validate on another supported screen size/density when available; avoid hardcoded display dimensions. If only one device is available, state that limitation.
5. Reuse existing reporting, TestListener, and hooks. **Do not create reporting classes, report generators, new listeners, or duplicate diagnostic capture.**
6. Final summary: every **TC-ID → TestNG method → PASS / FAIL / BLOCKED / NOT EXECUTED**, changed files, verified locators and match counts, original and replacement locator evidence (in this summary, not in code comments), total lookup budget, actual Maven/TestNG execution results, account-sensitive submissions appended to `.cursor/account-sensitive-executions.json`, app defects vs automation defects, test environment limitations, and unresolved blockers. Never claim an unexecuted test passed. Never claim a TC-ID was rerun when the execution record blocked it.

Wait for the user's first test-case module before implementing application tests.
